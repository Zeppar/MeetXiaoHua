遇见小花猫：做减法，转向「熟面孔」

评审范围：release 分支（含提交 09a01fa）2026 年 11 月微信小程序 + 微信云开发
视觉系统和产品气质在同类产品里少见，但功能概念太多，「线下拍猫」和「线上小屋」两套玩法几乎没连上。 下一步最该做的是减法，把产品重心从收集品种转到再次遇见同一只猫。 团队已经做出来的查重和 DINOv2 识猫，正好是这次转向的技术底子。

现状速写

核心流程

街上拍到猫→ 抠成白边贴纸卡→ 进图鉴（按品种计进度）→ 记到足迹地图→ 放进小屋（最多 3 只）→ 出门串门，寄回明信片→ 别人的猫来访 · 放生 / 收养→ 再遇见时存进「记忆」

做得好的

  • 视觉系统完整：颜色语义、胶带、邮戳、橡皮章、明信片都有规范文档，品牌辨识度高。
  • 隐私意识好：位置模糊到街区，只有自己能看到。
  • 异步陪伴有分寸：出门和明信片借鉴了《旅行青蛙》的「等待 + 惊喜」，不逼用户每天上线。

主要风险

  • 概念超过 13 个：图鉴、小屋、出门、来访、放生、收养、记忆、足迹、明信片、家具、背景解锁、护理、品种审核。
  • 拍猫是线下低频行为，小屋是线上高频行为，两者之间只靠「解锁背景」相连。
  • 街上大多是田园猫、狸花、橘猫，按品种算收集进度很快就会卡住。
竞品格局

谁在做相近的事

类型代表产品和我们的关系可借鉴
街猫收集游戏
海外热门		Cat Collector、Meowdex、PoCats、CatchCat、Chonk Finder最直接的竞品：拍真猫 → 收集成卡 → 显示在地图上Cat Collector 的每日小游戏和宝石节奏；Meowdex 只上传抠图、原图留在本机；CatchCat 的稀有度和对战
个体识别 / 熟面孔Catdex（开源）、MeetCats 喵出没、中大猫谱都在回答「这是哪一只」，而不是「这是什么品种」从照片认出同一只猫，记录每次目击和剪耳（绝育标记）状态
国内已上架 AppMewhere拍照识别、流浪猫档案、日历切地图同一批记录用日历和地图两种视角浏览
社区猫谱中大猫谱及各高校猫谱小程序验证了「一群人共同维护猫档案」的需求共建档案、公告、救助信息
异步养成旅行青蛙、Neko Atsume（猫咪后院）小屋和出门玩法就是这条路等待感、随机明信片、「猫只在你不在时来」
云养猫街猫（智能猫屋 + 直播 + 云投喂）公益加线上陪伴，靠用户打赏抽成「线上互动能真实帮到街猫」的动机很强，但商业模式有争议
我们的空位：海外竞品基本是「宝可梦式收集 + 竞争」，国内多是「救助 / 档案工具」。「真实相遇 + 情感手帐 + 异步陪伴」这个组合目前没人做，值得守住。如果继续往「品种收集」走，就会落进 Cat Collector 们已有先发优势的赛道。
产品方向

八条建议，按优先级

P0先做P1近期P2中期P3留口子
P0

从「品种图鉴」转向「个体档案 · 熟面孔」

原因
街猫品种单一，品种收集很快卡住，用解锁背景作奖励等于惩罚真实使用。真正打动人的是「又见到它了」，MeetCats、Catdex 都押在这里。我们已经在 cat-identity.js 里做了照片指纹、感知哈希和 DINOv2 特征比对。
怎么做
图鉴按「每一只猫」组织，每只猫一条「第 N 次遇见」时间线；收集维度改成遇见次数、认识天数、它的地盘；品种降为普通标签。
P0

砍掉或简化「品种审核」

原因
审核需要人工运营，对用户价值低。而且卡片详情页的「通过审核（调试）」按钮（card-detail.wxml:35）对所有用户可见；云端没配置 ADMIN_OPENIDS 时，用户还能自己审核通过自己的卡，这个流程实际在空转。
怎么做
品种让用户自己改、不审核，或只并列展示「识别结果」和「用户选择」两个字段。
P1

把线下拍猫和线上小屋连起来

原因
两套玩法之间只靠「解锁背景」相连，太弱。
怎么做
真实再遇见时，这只猫在小屋的亲密度大涨或解锁专属动作，小屋里的互动只给少量亲密度；明信片写「它最近常在 XX 街区出没」（用模糊过的足迹），给用户出门找它的理由；四条护理属性简化成一个亲密度加随机小事件，避免冲淡「真实街猫」的定位。
P1

减少一半概念，缩短新手路径

原因
小程序用户「用完即走」，首次体验要在 30 秒内拿到「贴纸卡」这个高光时刻。
怎么做
首屏只留「拍一只猫」；小屋等用户有 2 只猫后再解锁；放生、收养藏进次级入口。
P1

定位改为可选

原因
现在的文案是「不开定位就无法保存这只猫」，在保存这一步把用户挡住，转化损失大；微信对强制索取隐私权限审核也严。
怎么做
没有定位也能保存，事后补地点；地图上用「未标注地点」分组展示。
P2

用微信社交链代替「模拟邻居」

原因
用户量少时，串门大多是跟 mock_ 模拟主人。小程序最大的优势是分享卡片和群聊，旅行青蛙就是靠晒明信片传播开的。
怎么做
明信片和猫卡做成可分享的卡片或海报；「让我的猫去好友家串门」改成邀请制；中长期做「小区 / 校园猫谱」共建空间，位置照样模糊化。
P2

改「放生 / 收养」的说法

原因
面对真实流浪猫，「收养」容易被理解成真的领养，「放生」听起来像在说真猫。
怎么做
改成明确指向卡片的说法，如「送它去流浪 / 收下它的卡片」，或把机制换成「交换猫卡」。
P3

商业化留好口子

方向
家具、背景、明信片皮肤等外观付费；把自己的猫贴纸印成实体贴纸或明信片（最贴合手帐调性）；公益联动，把用户行为换算成对街猫投喂或绝育的捐赠，避开街猫打赏抽成的争议。
UI

六条 UI 建议

P0

对比度不达标

次要文字和主按钮都没达到 WCAG AA 的正文要求（4.5 : 1）。最小字号 20rpx 约等于 10px，户外阳光下更难看清，而拍猫恰恰在户外。下面是真实色值的对照：

次要文字 #9a8f842.9 : 1不达标现在的 --color-muted
白字 · 按钮 #e8743a3.0 : 1不达标渐变较浅的一端 #f7a56e 更低
次要文字 #7a6e634.7 : 1达标建议的新 muted
白字 · 按钮 #b8551f4.8 : 1达标即现有 --color-primary-ink

另一种做法：保留橙色按钮底，文字改成暖黑 #2b2622（约 6 : 1）。正文最小字号建议收到 24rpx。

P1

拍照保存的流程太长

现状
拍照 → 抠图 → 查重（最长约 7.5 秒）→ 备注弹窗 → 地点弹窗 → 定位 → 保存，中间被打断三次。
建议
拍完直接出贴纸卡，点一次「收下」就保存；备注、地点之后在详情里补；查重放后台跑，用一条轻提示告诉用户「这可能是你认识的 XX」。
P1

地图设置面板太偏开发者

现状
「最小 / 最大缩放级别」「最大倾角」「3D 楼块」都是调试参数。
建议
只留「平面 / 立体 / 卫星」两三个预设，其余参数收进开发版。
P2

小屋页信息太密

现状
room.wxml 416 行，同一场景叠了护理条、家具、访客、报告、出门状态和工具栏。
建议
每个状态只突出一个焦点：有访客时访客是主角、护理条收起；家具编辑做成单独模式。
P2

手写字体在不同手机上不一致

现状
--font-hand 依赖系统楷体，安卓会退回宋体，「手写感」在一半用户手机上不存在。
建议
用 wx.loadFontFace 加载手写字体的常用字子集，或改用颜色和便签纸底表达「手写」。
P3

视觉统一的小清理

清单
app.json 里 tabBar 选中色还是绿色 #22C26A，和品牌色不一致；assets/illus 下 4 张 AI 3D 黏土风位图已无引用（约 150KB），另外两张只剩调试样例在用，和「只用扁平 SVG」的规范矛盾；小屋「推进」按钮由常量 DEBUG_FAST = true 控制，建议和详情页调试按钮一起统一改用 isDevBuild()。
识猫方案

中大猫谱的猫脸识别，比我们的好吗？

简短回答：不适合拿来替换我们的方案，它解决的是另一个问题。但它点出了我们的短板：现有比对认不出换了角度的同一只猫。开源界有更合适的个体识别模型，用之前要注意许可证。

中大猫谱 cat-face我们现在（release）
问题类型封闭集分类：从一份固定的已知猫名单里选开放集检索：判断是不是用户见过的猫，见不到就是新猫
流程YOLOv5 框出猫 → DenseNet121 分类（128px；找不到猫时用 224px 全图模型兜底）→ 返回前 20 个候选文件 SHA-1 精确比对 + 全图 / 抠图感知哈希 + 颜色统计；可选 DINOv2-S 384 维特征，余弦 ≥ 0.8 算候选；返回前 3 个由用户确认
每只猫需要至少 10 张高质量照片1 张即可
加入新猫要用 GPU 重新训练整个模型不需要训练
「没见过」怎么判断不判断，总会返回已知猫的排名低于阈值就当新猫
适合谁猫群固定、有管理员维护照片的校园每个用户各自的猫，新猫不断出现
短板不支持我们的「每人一本手帐」场景；分类网络没加载预训练权重，依赖大量照片线上默认没开特征比对（CAT_REID_ENABLED），实际只能认出几乎相同的照片；DINOv2 是通用特征，两只橘猫也会很像；0.8 阈值没用真实数据校准过

更合适的开源选择

候选

MegaDescriptor（WildlifeDatasets）

是什么
专门在多种动物个体识别数据集上训练的特征模型（Swin 结构），输出用于「是不是同一只」的特征向量，正好是开放集检索。配套工具包 wildlife-tools 带特征提取、相似度计算，还有把全局特征和局部特征点匹配结合起来的 WildFusion。
注意
许可证是 CC BY-NC 4.0（不可商用）。L-384 版约 2.3 亿参数、权重约 1.9GB，CPU 推理偏重；合集里还有 L-224 等其他版本。适合拿来做离线对照基准，上线商用要另找方案。
参考

PPGNet-Cat

是什么
针对野外流浪猫红外相机照片的个体识别，用余弦相似度比较特征，公开了模型权重。
注意
训练数据不公开，场景是相机陷阱而不是手机近拍，需要在我们自己的照片上实测。
推荐

DINOv2 微调 + 位置先验（我们自己的路线）

为什么
DINOv2 是 Apache-2.0 许可，可以商用，而且已经接进了 rembg-server.py 的 /api/embed。用户每次在「它在图鉴里吗？」里点确认，都是一条免费的「同一只猫」标注，越用越准。
加一层
MeetCats 的做法：同一只猫通常活动在同一个街区。用已经模糊过的足迹给候选加权，成本很低，误认会明显减少。
建议的验证步骤： ① 先建一个小评测集，比如 30 到 50 只猫、每只 3 到 5 张不同角度的照片，量出 Top-1 / Top-3 命中率和误认率； ② 在线上打开特征比对，用评测集校准阈值，并加上位置先验； ③ 离线对比 MegaDescriptor 和 DINOv2，看差距有多大； ④ 用用户确认积累的数据，对 DINOv2 做度量学习微调（如 ArcFace 或三元组损失）。
